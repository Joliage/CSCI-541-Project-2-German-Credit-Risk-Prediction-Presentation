Objective

What this project is about

The aim is to construct a model that can effectively determine the credit risk of credit applicants using the German Credit Risk dataset.

The dataset consists of various features such as credit amount, duration, age, and other relevant attributes, along with the target variable indicating whether the applicant is a good or bad credit risk. We train machine learning classifiers to predict whether a new applicant is likely to be a good or bad credit risk.

Why this matters

Credit scoring touches real lives: a wrong "bad" prediction can deny someone a home, a car, or working capital; a wrong "good" prediction costs the lender money. Choosing the right model, the right metric, and the right interpretation is consequential.

Dataset

The German Credit dataset

Hosted on OpenML as dataset_id = 31, the file dataset_31_credit-g.arff contains 1,000 loan applicants with 20 attributes plus one target.

Schema highlights

  • Numerical: duration, credit_amount, installment_commitment, age, existing_credits, num_dependents
  • Categorical: checking_status, credit_history, purpose, savings_status, employment, personal_status, property_magnitude, housing, job, and more
  • Target: class — either "good" or "bad"

Why drop_first=True?

Dropping one category per feature avoids the dummy variable trap — perfect collinearity between the encoded columns that would break linear models like Logistic Regression.

PART 02 / 06

Model
selection.

Three classification families — linear, tree, ensemble — each chosen for a specific reason.

Model Selection · Rationale

Three models, three roles

Model 01

Logistic Regression

A basic, understandable baseline. Works best when there's a roughly linear relationship between features and the log-odds of the target.

Model 02

Decision Tree

Models non-linear interactions between features. Easy to interpret. Handles numerical and categorical features natively but prone to overfitting if unconstrained.

Model 03

Random Forest

An ensemble of decision trees. Highly accurate with minimal tuning. Non-parametric, robust against overfitting, and reports feature importance for free.

Strategy

Start simple, escalate complexity, compare honestly. The simplest model that wins should be preferred for explainability — particularly important in credit decisions.

PART 04 / 06

Evaluate the
models.

Accuracy alone is misleading on imbalanced classes — we use precision, recall, and F1 per class to read each model honestly.

Evaluation · Metrics

Reading the classification report

Accuracy

How close predictions are to actual labels overall. Misleading on imbalanced data — a model that always predicts "good" would score 70%.

Precision

Of the applicants predicted "good", how many really were good? Penalizes false alarms — wrongly approving bad risks.

Recall

Of all the actually-good applicants, how many did we catch? Penalizes missed cases — wrongly rejecting good applicants.

F1 Score

The harmonic mean of precision and recall — a single number that balances both.

Business stakes

For a lender, the costliest error is approving a bad risk (false positive on class 1). That makes recall on class 0 (bad) the metric to scrutinize — and where our models will struggle most.

Random Forest winners

The confusion matrix — a Chapter 3 refresher

Géron, p. 109: "Each row in a confusion matrix represents an actual class, while each column represents a predicted class."

For our binary problem (bad = 0, good = 1) the four cells are:

  • TN — actually bad, predicted bad ✓
  • FP — actually bad, predicted good ✗ (approving a bad risk — costly)
  • FN — actually good, predicted bad ✗ (rejecting a good applicant — unfair)
  • TP — actually good, predicted good ✓

The diagonal (TN + TP) is correct. Everything off-diagonal is an error — and the two error types carry very different business costs.

Live Demo · Step 02

Precision & recall — from first principles

From Géron, p. 109 – 110

precision = TP / (TP + FP)

recall = TP / (TP + FN)

F1 = 2 · (P · R) / (P + R)

Apply to our model (predicting "good" = class 1):

  • Precision = 126 / (126 + 24) = 0.84
  • Recall = 126 / (126 + 15) = 0.89
  • F1 = 2 · 0.84 · 0.89 / (0.84 + 0.89) = 0.87

Live Demo · Step 02b

The precision / recall trade-off

Géron, p. 111: "Increasing precision reduces recall, and vice versa. This is called the precision/recall trade-off."

For the lender

Wants high precision on "good" — when the model approves, the approval should be reliable. Accepts lower recall (some good applicants wrongly rejected) to avoid bad approvals.

For the applicant / regulator

Wants high recall on "good" — every legitimate applicant should be approved. Accepts lower precision (some bad approvals slip through).

Géron's hard question

"If someone says, 'Let's reach 99% precision', you should ask, 'At what recall?'" — p. 115

In our model the default threshold (0.5) gives precision 0.84, recall 0.89 on the "good" class. We'll see in the next step what happens when we raise the bar.

precisions, recalls, thresholds = precision_recall_curve(y_train, y_scores_good)

# Find the lowest threshold that yields >=90% precision
idx_for_90 = (precisions >= 0.90).argmax()
threshold_for_90 = thresholds[idx_for_90]
print(f"Threshold for >=90% precision: {threshold_for_90:.3f}")

# Apply the new threshold
y_train_pred_strict = (y_scores_good >= threshold_for_90)
print(f"Precision: {precision_score(y_train, y_train_pred_strict):.3f}")
print(f"Recall:    {recall_score(y_train, y_train_pred_strict):.3f}")
Threshold for >=90% precision: 0.728 Precision: 0.901 Recall: 0.512
The price of 90% precision

Raising the bar from 0.5 to 0.728 buys us a more reliable approval — but recall on "good" collapses from 0.89 to 0.51. We'd now reject roughly half of the truly creditworthy applicants. That's the trade-off, in numbers.

PR vs ROC — Géron's tip (p. 117)

"Prefer the PR curve whenever the positive class is rare or when you care more about the false positives than the false negatives. Otherwise, use the ROC curve." For credit risk, the costly error is a false positive (approving a bad risk) — so the PR curve is the honest one to publish, even though ROC AUC = 0.82 looks better in a slide.

Key Findings

What this project taught us

Simple often wins

On a small (1,000 rows), heavily one-hot-encoded dataset, Logistic Regression edged out Random Forest. Complex models need more signal to outperform simple ones.

Default ≠ bad

GridSearchCV barely moved either model's accuracy. The scikit-learn defaults are tuned for the common case for a reason.

Imbalance hides in accuracy

An 80% accuracy looks great until you see recall on class 0 stuck around 0.44 – 0.59. The minority class — the one a lender most needs to detect — is where every model is weakest.

Feature importance is intuitive

credit_amount, age, and duration topped the chart. The model encodes the same factors a human loan officer would weigh.

Limitations

Where this model breaks

  • Class imbalance — 70/30 split makes accuracy a misleading headline metric. Without resampling (SMOTE, class weights) or threshold tuning, the model under-predicts the costly "bad" class.
  • Small sample size — 1,000 rows is tight. Most variance in CV scores is sample noise. A real production model would need orders of magnitude more.
  • Dataset is old — the German Credit dataset dates to the 1990s. Real-world credit behavior, products, and demographics have moved on.
  • No temporal validation — credit risk drifts with the economy. A train/test split doesn't simulate the "trained-in-2020, deployed-in-2024" reality.
  • No calibration check — these models output class labels, not well-calibrated probabilities. For credit scoring, calibrated probabilities matter more than 0/1 predictions.
  • One metric, one threshold — accuracy at threshold 0.5 hides the precision-recall trade-off curve. A real deployment would tune the threshold to the business cost ratio.
Ethical Reflection

Credit risk modeling is not neutral

Discrimination Risk

The dataset contains personal_status (which mixes sex and marital status), foreign_worker, and age. In most jurisdictions, using these directly for credit decisions is illegal — and even when removed, the model can still learn proxies for them through correlated features.

  • Disparate impact — feature importance showing "age" as a top driver means younger applicants are systematically scored more pessimistically. That's exactly the kind of bias regulators look for.
  • Proxy variables — postal code, occupation, and savings_status can stand in for protected attributes even when those attributes aren't fed in directly.
  • Transparency — under regulations like ECOA in the US and the EU's GDPR / AI Act, applicants are entitled to an understandable reason for adverse decisions. That favors Logistic Regression (which gives you a coefficient per feature) over Random Forest's opaque ensemble.
  • Fairness auditing — before any deployment, we'd compute approval rates, false-negative rates, and calibration across protected demographic subgroups, not just overall accuracy.
Future Work

Where we'd take this next

Handle Imbalance

Apply SMOTE or class-weighting to improve recall on the minority "bad" class — the metric a lender actually cares about.

Try Stronger Models

Gradient Boosting (XGBoost, LightGBM), Support Vector Machines with RBF, and a small feedforward neural network.

Probability Calibration

Apply Platt scaling or isotonic regression so the model's output probabilities reflect actual default rates.

Cost-Sensitive Threshold

Pick the decision threshold to minimize the bank's expected loss, not the misclassification count.

Fairness Audit

Measure equalized odds and demographic parity across age, foreign_worker, and personal_status before deployment.

Explainability Layer

Use SHAP values to explain individual decisions — required for adverse-action notices under credit regulations.
